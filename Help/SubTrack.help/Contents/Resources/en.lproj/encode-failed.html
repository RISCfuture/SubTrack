If a run starts and then fails

A different moment and a different problem from a file that was never readable: FFmpeg launched, worked for a while, and stopped. The row says SubTrack couldn’t process the video and reports the code FFmpeg exited with, which on its own tells you nothing. The real message is in the activity log — read it before you guess.

What it usually is

  • The disk filled up. Slimming writes a whole new file, so the output needs room alongside the original until the run finishes.
  • The destination went away mid-run — an external drive unmounted, a network share dropped.
  • A track in the source is damaged. A rip with a bad patch can inspect cleanly and still fail when FFmpeg reaches the damage.

SubTrack also checks the file it just wrote, so a run can fail at the very end: an output missing tracks it should have, or a track with no data in it, is reported as a failure rather than as done. That’s a deliberate refusal to hand you a file that’s quietly wrong.

If it never started

Some failures report no exit code at all, because SubTrack refused the run before launching FFmpeg: it weighs the file the run would write against the room the destination volume has, and stops when the file plainly won’t fit. The row names both figures, and the activity log has nothing to add — nothing ran. Free up space on that volume, or save the queue’s output somewhere else, then start the row again.

That check is a courtesy rather than a guarantee. A transcode’s output size can’t be projected, and some volumes don’t report their free space, so a disk can still fill up partway through and fail the way the rest of this page describes.

Try again

A failed row can be started again. Fix the cause, then choose Queue ▸ Start Selected (⌘Return).
